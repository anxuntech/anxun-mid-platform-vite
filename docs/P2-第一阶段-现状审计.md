# P2 第一阶段现状审计

审计日期：2026-07-26
审计基线：`031ef0d1e459e0a5522e45815f69ddedff709b76`
审计范围：前端登录、后端认证、项目与企业数据范围、草料接口、政府端真实数据接口、下载能力和数据库结构。
执行边界：本报告只记录现状，不实施认证、数据库迁移或线上切换。

## 1. 总体结论

当前系统已经具备 P2 所需的数据隔离底座，但尚未具备可向应急局或人保正式发放账号的后端身份体系。

- P1 已建立 `county -> project -> company -> business_record` 数据关系，真实数据查询也固定按 `project_id='pingxiang'` 和数据环境过滤。
- 真实数据聚合接口已通过内部密钥或 ECS 本机访问进行临时保护，匿名访问会被拒绝。
- 现有中台登录是浏览器端演示能力：账号、明文密码、角色和企业范围都打包在前端，登录状态保存在 `localStorage`，可以被用户自行伪造。
- `/gov/pingxiang` 当前是独立的公开演示路由，不经过中台登录判断；生产真实数据尚未公开，这是正确的 P1 安全边界。
- 后端没有用户、密码哈希、会话、角色、项目绑定、登录审计或下载审计表。
- 当前没有正式服务端导出接口。平乡阶段报告由浏览器直接基于当前页面数据生成 HTML 文件，无法形成后端下载授权和审计。

因此，P2 的核心不是增加一个登录页面，而是把“身份、项目范围、记录范围、下载权限”全部移到后端裁决。

## 3. 当前仅为前端展示、没有后端控制的能力

### 3.1 账号和密码

- `src/auth.ts:23-30` 在前端源码中保存完整测试账号和明文密码。
- `src/auth.ts:56-65` 在浏览器中直接比较账号和密码。
- 任何访问前端静态资源的人都能查看这些账号信息；这些账号不能视为正式账号。

### 3.2 登录状态

- `src/auth.ts:68-96` 使用 `localStorage` 保存和恢复会话。
- `src/App.tsx:1572-1592` 的登录和退出均只改变浏览器状态，没有向后端验证或撤销会话。
- 用户可直接编辑 `localStorage` 伪造角色、用户名和企业范围。
- 不存在空闲超时、最长有效期、账号禁用后会话失效或服务端主动撤销能力。

### 3.3 页面和角色权限

- `src/auth.ts:48-54` 通过前端映射隐藏导航。
- `src/App.tsx:1482-1521` 在浏览器中判断可访问页面和企业编号。
- 这些逻辑只改善界面体验，不能保护后端接口，也不能作为正式授权依据。

### 3.4 企业范围

- `src/App.tsx:632-642` 在前端数组中计算企业范围。
- `src/App.tsx:1496-1521` 只在前端修正 URL 中的企业筛选。
- 当前真实数据聚合接口一次返回整个平乡项目数据，没有基于登录用户进一步限制企业范围。

## 4. 后端认证与接口保护现状

### 4.1 当前接口清单

| 方法与路径 | 当前保护 | P2 判断 |
| --- | --- | --- |
| `POST /api/caoliao/webhook` | 可配置共享密钥；默认配置值为未强制 | 保留机器接口，生产必须强制密钥；不纳入浏览器会话。 |
| `GET /api/caoliao/health` | 匿名 | 可继续仅返回健康状态，不得暴露运行配置。 |
| `GET /api/caoliao/events` | 内部密钥或受控本机 | P2 应仅允许 `admin` 内部诊断，且默认不返回完整原始载荷。 |
| `GET /api/caoliao/service-records` | 内部密钥或受控本机 | 不能直接转为面向用户接口，应通过项目范围查询层提供。 |
| `GET /api/caoliao/hazards` | 内部密钥或受控本机 | 同上。 |
| `GET /api/gov/pingxiang/dashboard` | 内部密钥或受控本机 | P2 应改为正式用户会话 + 项目绑定校验。 |

路由证据：`server/routes/caoliaoRoutes.js:9-38`、`server/routes/govPingxiangRoutes.js:3-9`。

### 4.2 主要缺口

- `server/security/requestAuth.js` 只认识 Webhook 密钥和内部数据密钥，不认识用户身份、角色或项目范围。
- `server/routes/index.js:17-36` 没有统一认证中间件链。
- `server/controllers/govPingxiangController.js:24-26` 在通过内部密钥后直接构建整个平乡项目数据。
- `server/index.js:8-13` 对所有来源返回 `Access-Control-Allow-Origin: *`，与同域 Cookie 会话不兼容，也不符合正式环境最小来源原则。
- 后端没有基础安全响应头、登录限速、会话 Cookie、CSRF 校验或用户操作审计。
- 现有数据读取接口无用户级 `401/403/404` 语义，只有内部密钥失败时的 `401`。

## 5. 县域、项目和企业隔离现状

### 5.1 数据库能力

数据库已经存在：

- `counties.county_id/county_slug`
- `projects.project_id/county_id/project_slug`
- `companies.company_id/project_id`
- `business_records.county_id/project_id/company_id`

对应证据：`database/migrations/001_initial_schema.up.sql:7-40`、`:94-118`。

这意味着 P2 无需复制平乡业务表，也无需为每个县域建立一套数据库。

### 5.2 当前运行限制

- `server/services/govPingxiangMysqlService.js:3` 将项目固定为 `pingxiang`。
- 所有企业、记录和附件查询均附加该固定项目和数据环境条件，见 `server/services/govPingxiangMysqlService.js:53-109`。
- 该固定过滤能避免当前接口跨项目读取，但它不是账号隔离：任何能通过内部密钥的人都能读取整个平乡项目。
- 当前没有 `user_projects` 或用户企业授权关系，后端不能判断某个应急局、人保或管理员账号的范围。
- 记录详情目前由前端从聚合结果中查找，没有后端按“用户项目范围 + record_id”再次校验的详情接口。

### 5.3 越权风险

P2 正式开放前，如果直接把现有内部数据密钥交给浏览器，将出现以下严重风险：

1. 密钥会进入前端包或网络请求，可被复制。
2. 持有密钥的用户可直接调用整个平乡聚合接口。
3. 后续若增加其他项目而查询层未强制使用服务端范围，可能通过参数或记录编号跨项目访问。
4. 企业联系方式和附件 URL 会随整个项目聚合结果返回，无法按角色脱敏。

因此，内部数据密钥不得下发浏览器；正式页面必须使用服务器会话。

## 6. 平乡页面与演示/真实环境现状

- `src/App.tsx:1480` 和 `:1933-1935` 将 `/gov/pingxiang` 作为独立页面，绕过当前中台伪登录。
- `src/features/pingxiang-gov/usePingxiangDashboardData.ts:106-122` 在生产默认固定为 `demo`；只有开发环境查询参数可以请求真实模式。
- `src/features/pingxiang-gov-v2/PingxiangGovPlatformV2.tsx:59-72` 明确显示演示或真实数据状态。
- 当前公开页面保持演示数据、真实接口匿名返回 `401`，符合 P1 封板要求。

P2 完成前不得改变该行为。P2 上线切换时，应将公开演示迁至明确的 `/gov/pingxiang-demo`，正式 `/gov/pingxiang` 才在后端认证完成后启用真实数据。

## 7. 下载和报告现状

- 当前没有后端报告或 Excel 下载接口。
- `src/features/pingxiang-gov-v2/PingxiangGovSecondaryPagesV2.tsx:325-354` 在浏览器内把当前演示数据拼成 HTML，并通过 `Blob` 下载。
- `src/features/pingxiang-gov-v2/BusinessComponents.tsx:135-150` 的打印/演示导出同样是纯前端动作。
- 这些演示功能没有登录校验、角色校验、项目范围复核和下载日志，但当前只包含明确标识的演示数据。

P2 不应给这两个前端按钮直接接真实数据。正式下载必须由后端重新解析会话和项目范围，生成文件并写入下载审计；原始 Webhook payload 和附件批量包在 P2 默认禁止。

## 8. 数据库与依赖缺口

现有迁移 `001` 至 `004` 中没有：

- 用户表；
- 密码哈希字段；
- 用户项目绑定表；
- 服务器会话表；
- 登录/退出/敏感详情访问审计表；
- 下载审计表。

`package.json` 也没有 Argon2id/bcrypt、Cookie 解析、限速或会话依赖。P2 应采用最小依赖增量，不升级现有 React、Vite、MySQL 驱动或四类数据链路依赖。

## 9. 敏感信息检查结论

- 跟踪文件中未发现私钥、证书、AccessKey、非空数据库密码、非空 Webhook 密钥或完整数据库连接串。
- `.env.example` 只包含空值模板。
- `src/auth.ts:23-30` 包含公开演示账号和明文密码。虽然不是生产密钥，但必须在 P2 实施阶段从前端包中删除，且不得复用为正式账号密码。
- P2 文档、迁移、种子脚本和测试不得写入真实密码；正式初始密码只允许通过受控命令输入或安全渠道交付。

## 10. 风险等级与处理优先级

| 等级 | 风险 | P2 处理 |
| --- | --- | --- |
| 阻断 | 前端明文账号和可伪造 `localStorage` 会话 | 正式账号启用前必须删除并替换为后端会话。 |
| 阻断 | 政府端没有用户项目绑定和后端资源范围校验 | 正式真实页面启用前必须完成。 |
| 阻断 | 下载没有服务端授权与审计 | 正式下载启用前必须完成。 |
| 高 | CORS 为 `*`，缺少同域 Cookie/CSRF 策略 | 正式会话上线前必须收紧。 |
| 高 | 原始草料事件接口可由内部密钥读取完整载荷 | 仅限管理员诊断，默认裁剪字段；不得面向项目查看者。 |
| 中 | 平乡真实查询项目 ID 硬编码 | P2 改为从已授权项目解析，但不扩展跨县域 UI。 |
| 中 | 无登录失败限速、禁用账号会话撤销和审计 | P2 会话上线时同步完成。 |

## 11. 第一阶段审计结论

当前平台不能安全地直接向应急局或人保发放正式账号。P2 的最小可行改造应严格限定为：

1. 两类角色：`admin` 和 `project_viewer`；
2. 应急局与人保使用不同账号和 `organization_name`，但共享只读角色；
3. 后端密码哈希、服务器会话、账号禁用和退出；
4. 用户与项目绑定；
5. 所有正式政府端 API、详情和下载在后端强制项目范围；
6. 汇总下载与原始明细分权并记录审计；
7. 公开演示与正式真实页面分离；
8. P1 数据模型、四类入库链路和 `anxun_runtime` 账号保持不变。
